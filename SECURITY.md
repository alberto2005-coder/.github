# Security Policy

## English

### Supported versions

Security fixes are applied to the `main` branch and to the latest published release of each repository. Older versions may not receive updates; if you are using an old version, upgrade before reporting an issue.

### How to report a vulnerability

**Do not open a public issue** for security vulnerabilities.

Report them through **GitHub Security Advisories**: in the affected repository, **Security** tab → **Report a vulnerability**. The whole conversation stays inside GitHub, which lets us coordinate the fix and the disclosure privately. No email is needed or offered.

Please include, as far as possible:

- Repository and affected version, release or commit.
- Type of vulnerability and expected impact.
- Steps to reproduce it, or a minimal proof of concept.
- Required configuration (operating system, browser, permissions, environment variables).
- Mitigation or fix you propose, if you have one.

### In scope

- Source code owned by this account's repositories.
- GitHub Actions configuration and publishing workflows.
- Passwords, keys or tokens exposed in code or in the history.

### Out of scope

- Vulnerabilities in third-party dependencies, libraries or services. Report them to the original project.
- Denial of service, spam, social engineering or physical access attacks.
- Issues that require a deliberately insecure configuration, or credentials already compromised by third parties.
- Best-practice suggestions with no demonstrable real impact.

### Expected timelines

- **Acknowledgement**: 72 business hours.
- **Initial assessment**: 7 days.
- **Fix**: depending on severity and complexity; it will be agreed with you.
- **Disclosure**: coordinated, 90 days by default, or earlier if a fix has been published.

This is a personal project maintained on a best-effort basis; these timelines are a good-faith commitment, not a service level agreement.

### Credit

If you wish, you can be credited in the release or in the security advisory. Say so in the report and tell me which name or link you want to appear. There is no bug bounty program.

## Español

### Versiones soportadas

Se aplican correcciones de seguridad a la rama `main` y a la última release publicada de cada repositorio. Las versiones anteriores pueden no recibir actualizaciones; si usas una versión antigua, actualiza antes de reportar un problema.

### Cómo reportar una vulnerabilidad

**No abras un issue público** para vulnerabilidades de seguridad.

Repórtalas con **GitHub Security Advisories**: en el repositorio afectado, pestaña **Security** → **Report a vulnerability**. Toda la conversación se queda dentro de GitHub, lo que permite coordinar la corrección y la divulgación de forma privada. No hace falta correo y no se ofrece ese canal.

Incluye, en la medida de lo posible:

- Repositorio y versión, release o commit afectado.
- Tipo de vulnerabilidad e impacto esperado.
- Pasos para reproducirla o una prueba de concepto mínima.
- Configuración necesaria (sistema operativo, navegador, permisos, variables de entorno).
- Mitigación o corrección que propongas, si la tienes.

### Qué está dentro del alcance

- Código fuente propio de los repositorios de esta cuenta.
- Configuración de GitHub Actions y flujos de publicación.
- Contraseñas, claves o tokens expuestos en el código o en el historial.

### Qué queda fuera del alcance

- Vulnerabilidades en dependencias, librerías o servicios de terceros. Repórtalas al proyecto original.
- Ataques de denegación de servicio, spam, ingeniería social o acceso físico.
- Problemas que requieran una configuración deliberadamente insegura o credenciales ya comprometidas por terceros.
- Buenas prácticas sin impacto real demostrable.

### Plazos orientativos

- **Acuse de recibo**: 72 horas laborables.
- **Evaluación inicial**: 7 días.
- **Corrección**: según la gravedad y la complejidad; se acordará contigo.
- **Divulgación**: coordinada, por defecto a los 90 días o antes si hay una corrección publicada.

Este es un proyecto personal mantenido en la medida de lo posible; estos plazos son un compromiso de buena fe, no un contrato de nivel de servicio.

### Reconocimiento

Si lo deseas, puedes ser acreditado en la release o en el aviso de seguridad. Indícalo en el reporte y con qué nombre o enlace quieres aparecer. No hay programa de recompensas económicas.
